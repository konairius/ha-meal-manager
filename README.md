# Meal Manager for Home Assistant

LLM-generated meal plans that run entirely locally. Every dish and the shopping list are generated by
a local model through Home Assistant's **AI Task** building block, so any local model integration
that provides an AI Task entity (e.g. Ollama) works. The integration never talks to an LLM or the
internet itself.

Requires an AI Task entity that supports *generate data* with structured output and a model that
follows instructions reliably.

## Features

- **Plan generation** for 1–31 days, as a *suggestion* (draft) you review before accepting.
- **Settings** for portions, effort, health level, calories per day and meals per day. Each one is a
  fixed value, an entity (state or attribute), or an entity with a fixed fallback, e.g. the calorie
  need exported by your fitness app or `zone.home` for the number of people at home.
- **Overrides** per weekday, per meal, or per weekday + meal.
- **Cooked tracking**: tick meals off; when every meal is cooked a new suggestion is created and the
  `meal_manager_draft_ready` event fires.
- **Decline** a meal ("something else") or **ban** it ("never again"); bans can be lifted.
- **Calories** are split across the day's meals and portion sizes are scaled (0.75×–1.5×) to match.
- **Shopping list**: the model turns the ingredients of all uncooked meals into products as they are
  sold ("Kokosmilch: 2 Dosen à 400 ml", "Petersilie: 1 Bund"), without what is always in stock, and
  it is pushed to any to-do list.
- **Language**: recipes and shopping list in German or English.
- **Entities**: calendar, plan status, next meal, today's meal per meal slot.
- **UI**: mobile-first dashboard card and a *Meal plan* sidebar panel, English and German.

## Installation (HACS)

1. HACS → ⋮ → *Custom repositories* → add `https://github.com/konairius/ha-meal-manager`, type
   *Integration*.
2. Install **Meal Manager** and restart Home Assistant.
3. *Settings → Devices & services → Add integration → Meal Manager*.
4. Open *Meal plan* in the sidebar, or add the card to a dashboard.

The card and panel are served by the integration itself; no dashboard resource has to be added.

## Configuration

Everything is edited under *Settings → Devices & services → Meal Manager → Configure*:

| Menu | Contents |
| --- | --- |
| General | AI Task entity, household preferences, shopping list (to-do entity, what is always in stock), language of recipes and shopping list, days per plan, how many recently cooked dishes to avoid, seasonal produce, automatic new plan, sidebar panel |
| Default settings | Value and/or entity (+ attribute) for portions, effort, health and calories |
| Meals of the day | Meals per day, and per meal (breakfast, lunch, dinner, snack): whether it is planned at all, time, share of the daily calories and priority |
| Add / remove override | A value and/or entity for one setting on a weekday, a meal, or both |

### How settings are resolved

Per day and meal, from the most specific layer to the least specific:

```
weekday + meal  >  meal  >  weekday  >  default  >  built-in
```

The first layer that yields a valid value wins. An entity that is `unavailable`, `unknown` or not a
valid number falls back to the fixed value of the same layer, then to the next layer, so a flaky
sensor never blocks planning. The card's *Settings* tab shows the resolved values for the next seven
days and where each one came from.

| Setting | Scope | Values | Built-in |
| --- | --- | --- | --- |
| `portions` | per meal | integer ≥ 1 | 2 |
| `effort` | per meal | 1 = low (≤ 20 min), 2 = medium (≤ 45 min), 3 = high; entities may also report `low`/`medium`/`high` | 2 |
| `health` | per meal | 1 (indulgent) … 5 (very healthy) | 3 |
| `calories` | per day | kcal per person per day; 0 = no target | none |
| `meals_per_day` | per day | 1 – 4 | 3 |

Only meals ticked as *Plan this meal* are ever suggested (by default breakfast, lunch and dinner;
snack is off). **Meals per day** then keeps the enabled meals with the lowest priority number
(defaults: dinner 1, lunch 2, breakfast 3, snack 4), so with two meals a day you get lunch and
dinner. For one meal a day, untick all but that meal, or set meals per day to 1 (which keeps dinner),
for example only on weekdays with a weekday override.

### Local model

Every dish is generated by the AI Task entity chosen under *General* (empty: the preferred AI Task
entity under *Settings → System → General*). Each request carries the meal, effort, health level,
calorie target, household preferences, the season, the language, the dishes that must not be
suggested (banned, declined, already in the plan) and those cooked recently.

Answers are checked strictly: every ingredient must be `quantity | unit | name` with a unit of `g`,
`ml` or `pcs`, and the amount must be plausible for one portion (not 5 lemons, 1 kg potatoes or 6
garlic cloves). A broken answer, such as `5 | unit | lemon` or `2 | tbsp | oil`, is rejected and the
model is asked again together with the reason, up to three times. If there is still no usable
answer, generation fails with the `meal_manager_generation_failed` event and an error message.

### Shopping list

*Add to shopping list* (or `meal_manager.add_to_shopping_list`) sends the summed ingredients of all
uncooked meals to the model, which writes the shopping list:

- products as they are sold, with package sizes, rounded up (`Kokosmilch: 2 Dosen à 400 ml`,
  `Eier: 1 Packung (10 Stück)`, `Kartoffeln: 1,5 kg`), with the same product from different recipes
  merged;
- in the language chosen under *General* (German by default);
- without what is always in stock (*General → Always in stock*, free text sent to the model).

The answer must be one `product | amount` line per product, with no product twice and no more products
than ingredients; otherwise it is asked for again with the reason. Running it again replaces the open
items it added before, so nothing is duplicated; items you added yourself or already ticked off stay.

### Seasons

*General → Seasonal produce* tells the model the month and to cook for Central Europe:

| Mode | Effect |
| --- | --- |
| Only in season (default) | Only fresh produce that is in season now (e.g. no asparagus in October); canned, frozen or stored produce is fine. |
| Prefer in season | Seasonal produce is preferred. |
| Ignore seasons | Nothing is said about seasons. |

## Dashboard card

```yaml
type: custom:meal-manager-card
title: Food        # optional, "" hides the header
days: 1            # optional: only show this many days starting today
tabs: true         # optional: show the Banned and Settings tabs
```

## Actions

| Action | Data |
| --- | --- |
| `meal_manager.generate_plan` | `start_date`, `days` (both optional) |
| `meal_manager.accept_plan` / `discard_plan` | – |
| `meal_manager.mark_cooked` | `meal_id`, or `slot` (+ `date`, default today); `cooked: false` undoes |
| `meal_manager.decline_meal` | `meal_id` |
| `meal_manager.ban_meal` | `meal_id` or `title` |
| `meal_manager.unban_meal` | `title` |
| `meal_manager.add_to_shopping_list` | `draft`, `entity_id` (optional); returns the items |

Events: `meal_manager_draft_ready`, `meal_manager_plan_completed`, `meal_manager_meal_cooked`,
`meal_manager_generation_failed`.

Example: an NFC tag in the kitchen marks today's dinner as cooked.

```yaml
automation:
  - alias: Dinner cooked
    triggers:
      - trigger: tag
        tag_id: kitchen-dinner
    actions:
      - action: meal_manager.mark_cooked
        data:
          slot: dinner
```

Example: get notified when a new plan is waiting.

```yaml
automation:
  - alias: New meal plan ready
    triggers:
      - trigger: event
        event_type: meal_manager_draft_ready
    actions:
      - action: notify.mobile_app_phone
        data:
          message: A new meal plan is waiting for review.
          data:
            url: /meal-manager
```

## Entities

- `sensor.meal_manager_plan_status`: `none` / `active` / `completed`; attributes: cooked, total,
  draft_pending, bans
- `sensor.meal_manager_next_meal`: next uncooked meal, with ingredients and steps as attributes
- `sensor.meal_manager_today_<meal>`: one per meal of the day
- `calendar.meal_manager_meal_plan`: the active plan, one event per meal at the meal's time

## Architecture

```
custom_components/meal_manager/
  core/             framework-free domain and use cases (no Home Assistant imports, enforced by a test)
    models.py       Plan, PlannedMeal, Recipe, Ban, ...
    settings.py     settings model and layered resolution
    planner.py      MealPlanner application service (lifecycle, bans, history, shopping list)
    llm.py          recipe prompt and strict parsing of the model's answers
    quantities.py   quantity parsing and plausibility per portion
    shopping.py     shopping list prompt and strict parsing
    ports.py        interfaces the core depends on
  adapters.py       Home Assistant implementations of the ports (AI Task with retries, Store, bus, states, to-do)
  __init__.py       composition root, card and panel registration
  config_flow.py    settings UI
  services.py, websocket_api.py, sensor.py, calendar.py
  frontend/         card and panel (plain web components, no build step)
```

State is stored in `.storage/meal_manager`.
